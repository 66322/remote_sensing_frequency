# 实验启动交付、故障停止与跨对话复用规则

生效：2026-10-24。来源：用户在[启动复盘](../experiments/PHASE3_STARTUP_POSTMORTEM_20261024.md)后明确要求“写入相关文件，避免后续再出现，使以后换新对话也不影响”。以下为已采纳的长期执行要求，不再只是助手建议。研究合同及用户后续明确指令保持优先。

## 1. 接续已有运行先读记录

新对话依次读取远端START_HERE、研究决定、HANDOFF、PROJECT_STATUS、NEXT_EXPERIMENT及[跨对话执行约定](EXECUTION_CONTRACT.md)；[稳定接续入口](../current/NEW_CHAT_HANDOFF.md)只指向这些当前文件。核对最后观测、科学源与运行修订、run目录、已有检查证据及唯一下一步，再决定行动。日期入口或历史协议里的启动命令不得直接复用。

当前已有运行时，默认只读接续，不因缺少聊天记忆、观测过期、换电脑或发现新长期规则而重新预检、下载新运行包、重启控制器或修补运行快照。用户已明确授权的同一事项不重复确认。文档更新不触发GPU训练、CPU整轮审计或重新准备数据。

## 2. 新执行版本的最小完整交付验证

验证对象必须是用户实际获得的包和布局；开发仓库内测试只能证明其自身范围。下列检查按依赖顺序组织成一次有界目标预检，未变的已通过项引用原件直接复用；不得借本规则层层增加与当前变更无关的门槛。

| 范围 | 必须验证的事实 |
|---|---|
| 下载包完整性 | manifest自身及全部载荷真实落盘；离开完整仓库后入口可用；清单、载荷与登记SHA一致；没有借用开发目录中的额外模块 |
| 真实分包布局 | 按目标M2/combined等独立快照布置路径，执行真实入口和各阶段导入；检查模块文件来源及包搜索路径，覆盖同名常规包/命名空间遮蔽 |
| 目标环境 | 使用对应运行锁定的Python/Torch及依赖版本，不只检查CUDA可用；本轮版本要求不能擅自推广为所有后续实验统一版本 |
| 必要系统能力 | 对Linux匿名memfd等实际创建、映射与跨进程传递；Windows模拟或hasattr不能代替目标能力证明，也不允许私自降级磁盘数组缓存 |
| 真实模型与权重 | 使用同一实际模型构造函数、兼容副本和公共权重，CPU构造并严格加载，记录来源/摘要；Python语法或AST解析不能代替运行时导入 |
| 数据与生命周期 | 分阶段声明已有数据、新数据待就绪及禁止访问的split；核对本次必要的输入绑定和输出目录；新任务数据缺失进入其既定等待，不伪装为全部阶段已具备数据 |
| 调度与首败停止 | 检查公共工程故障会停止后续派发、保存原栈并清理自身拥有的子进程；不得只禁止同一ID重试却继续派发全部其他根作业 |

对新增或更改的入口做相应最小检查；目标检查由用户执行。沿用原环境时仅处理明确不兼容项，不能默认新建conda环境、升级无关包或因禁用xFormers的普通警告改环境。

CUDA前向/反传/optimizer路径用首个既定正式作业实际更新作为证据，不另加seed、超预算步数或独立训练探针。正式首更前的CPU检查与启动器派发分别报告。某阶段尚未真实执行时，保留其待验收边界；不得从M2已首更推断J/R/T/V均已跑通。

## 3. 不得再次遗漏的已知兼容点

| 本次教训 | 后续交付要求与可复用来源 |
|---|---|
| 清单只下载到内存而未写包 | 同一次清单原字节落盘并绑定；检查离线精简包，见[包遗漏修复](../experiments/PHASE3_COMBINED_BOOTSTRAP_FIX_20261023.md) |
| Python缺少os.memfd_create | 区分Python绑定、libc接口与内核能力；按已有同语义适配及目标FD传递证据处理，见[memfd接续](../experiments/PHASE3_M2_MEMFD_REPAIR_20261024.md) |
| Python3.9加载DINO联合类型注解失败 | 先查day_dino_compat及当前兼容副本；确认适配接到实际M2/J/R构造链，不能只让预检单独通过，见[DINO故障记录](../experiments/PHASE3_M2_PY39_IMPORT_FAILURE_20261024.md) |
| model常规包遮蔽另一快照的模型目录 | 不能只增加PYTHONPATH并在单仓库测试；复现目标分包布局，验证受控模块来源，见[model路径接续](PHASE3_MODEL_NAMESPACE_CONTINUATION_20261024.md) |
| 一个导入错误产生63条根作业失败 | 训练FAILED须触发全队列停止后续派发；现有运行期实现见[首败适配](../../scripts/phase3_engineering_runtime.py)，没有故障时不为验收主动中断当前实验 |

上述资料是已知问题与修复依据，不是要求重新执行旧修复命令。原源码、运行修订、独立兼容补丁分别绑定；不通过静默改原仓库、删除失败记录或全局隐式注入伪造原执行版本。

## 4. 故障处理固定顺序

1. 暂停新的派发并保存该run首个完整error/traceback、时间、作业ID及状态；只处理明确拥有的子进程，不能按名称批量kill或误伤其他作业。
2. 区分登记前失败、目标检查失败、模型导入前失败、发生优化后的训练失败、评价失败、数据待就绪与上传失败；合并监督器的下游停止消息不是上游根因。
3. 沿首个原始栈检查实际入口、环境、导入来源、数据/权重绑定和调用路径，按同类错误归组；明确是否已有progress、checkpoint、参数或优化产物，不能只看summary累计完整端点数推断零训练。
4. 在授权范围内修复受影响的工程链并验证。保留旧失败与执行来源，不覆盖科学合同、不热改运行快照、不删除锁/单次回执绕过重复启动。已有明确接续授权继续执行；不将一般失败自动重跑或加seed合理化。
5. 更新当前状态和唯一下一步；已完成的repair/bootstrap命令从当前入口移除或明确归为历史，不能尾部追加新段却保留矛盾行动。上传失败只续传已有文件，不重算训练或推理。

首败停止允许同时已有少量在途作业，不承诺所有故障只留一条记录；应阻止把公共错误继续放大成全批失败。工程导入失败、开发阴性与研究问题不成立分别报告。

## 5. 交付与交接最小字段

每次新版本交付或接续记录必须包括：

- 科学源、执行修订及额外补丁的提交/清单身份；实际run和数据来源、环境版本与唯一启动/状态入口。
- 各必要检查的证据路径、绑定与状态：本次通过、引用既有通过、因真实变更需查、尚未验证或不适用。未取得原件须写明终端节选/摘要的边界。
- 每阶段所需数据是否具备；哪些已入队、哪些仍是候选/条件扩展；数据等待位置与当前已授权下一步。
- 保留的最终端点、训练轨迹、原始整数计数、配置/采样流/来源绑定、失败记录；临时内存与rolling状态的回收条件；GitHub自动上传覆盖及仍需人工整理的材料。
- 最后观测时间及实际状态，明确“源码实现、本地检查、目标检查、控制器放行、正式优化更新、完整阶段验收、GitHub回读”的证据等级。

检查复用以原件绑定为依据；变化只重验受影响项，不因本表存在而补跑整链。状态查询不是新增资源审计。原件量大时按显式轻量清单上传GitHub，不要求用户反复粘贴长输出，不索要或暴露凭据。
