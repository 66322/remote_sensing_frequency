# D23吞吐代码审阅与优化边界

2026-10-01，读取846403ccc83c97731eceb199de99d9049039e64b分支快照的scripts/d23_engine.py、d23_lifecycle.py、run_rebuild_v1_d23.py及已有工程/预算记录。性质：代码审阅与重写版建议，无新增服务器测量，无提速实测结果，不改变当前队列。

## 已知事实

用户资源：两张H10080GB（物理0/1），主机RAM/磁盘充足；用户报告GPU利用率约30%，不是助手独立采样。既有预算显示GPU allocated峰值约2.44GiB。低利用率不是“必须再做完整资源审计”的理由。

代码的逻辑batch逐样本串行materialize；TileCache默认capacity=1；torch/OMP/BLAS线程被限制为1；缓存读取使用np.load的mmap模式。容量1造成对象轮换并不等于每次整tile从磁盘重读，操作系统页缓存可能复用数据。当前代码存在CPU数据准备和GPU计算未充分重叠的优化空间，但仅凭这些事实不能断言30%的完整成因。

既有不同测量场景中，GPU计时训练步骤约0.19秒，包含数据处理的步骤中位约0.57–0.62秒。二者不是配对的阶段计时，不能相减当作已测得的CPU耗时或承诺加速倍数。

## 优先优化顺序（尚未实现/部署）

1. 增大tile缓存并预取后续逻辑batch，保留确定性样本顺序和随机键；采用有界CPU并行处理，避免多进程过度争抢。12个6000×6000 tile若RGB/DSM为float32、标签uint8，仅数组理论量约7.34GB/进程，实际开销另计。用户充足RAM应合理使用。
2. 配合预取考虑固定内存和异步传输，正确同步；保留模型输入、损失、精度、有效batch及optimizer更新顺序。用改动范围内的短等价性检查验证，不另做全面审计。
3. 之后可评估每GPU两个独立实验并发，即双卡四任务。显存记录说明有空间，但CPU、内存带宽和评价峰值可能限制总吞吐；并发数提升不保证加速。必须由新调度版本管理独立输出和恢复，不能在现有队列旁手工重复启动相同组。

## 不能无条件增加的设置

- 当前没有梯度累积；专家micro8只分块前向，gate16两视图合并loss单次反传。
- 历史micro2/4/8输出一致，micro16出现可复现的预测差异，因此micro8为数值一致性选择，不是显存限制。
- 有效batch16改32且仍4000步会改变样本曝光与优化；尺寸、步数、精度、骨干变化也改变研究条件。若将来采用，应统一对照协议并明确新版本，不能承诺效果不变。
- 当前队列已经投入训练，不为了利用率数字立即停机/重跑。先保护已有产物；下一执行版本优先做上述工程优化。已完成验收直接复用，新错误或实质变更才做局部验证。

本审阅不证明语义/频率机制有效，也不替代最终八组结果比较。
